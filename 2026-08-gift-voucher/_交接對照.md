## G. 規格與現行分支相反的一組欄位（2026-09-21 Glen 定案）

D 區是「工程做了、規格沒記」，這一區是反過來：**規格定了，分支要跟著改**。

### 定案

券種層只有兩個控制，兩個都管**兌換端**：

| 畫面欄位 | 對應欄位 | 語意 |
| --- | --- | --- |
| **可兌換起日** | `PresentVoucherType.StartTime`（建議改名 `RedeemStartTime`）| 這一天之前，客人兌換不到。券照樣發得出去 |
| **開放兌換** | 分支現在是 `PresentVoucherType.Display`，**這個名字是錯的**，建議改 `IsRedeemable` | 關掉＝客人兌換不到，**含手上已經發出去的券** |

**兩者都不是「把券藏起來」。** 起日沒到、或開關關掉的時候，**前台照常看得到這張券**，只是兌換按鈕變成「**尚未到達兌換時間**」按不下去。所以這個開關的語意不是 Display——照字面實作的人會去改前台的顯示與否，那是錯的。

**沒有**「開始發券日」「停止發券日」「開放發券」這三個東西。要停止發券就把發券總量發滿，或單純不再操作發券。

`PresentVoucherType.EndTime` **本規格不使用**。券什麼時候失效，看單張券自己的到期日（`PresentVoucher.ExpireTime`）。

### 分支現在寫成什麼

`PresentVoucherService.Issue()` 第 164~166 行，三個欄位全部拿來擋**發券**：

```csharp
if (!type.Display)  → "券種 X 已停用，不再發新券"
if (now < type.StartTime) → "券種 X 尚未開始發放"
if (now > type.EndTime)   → "券種 X 已結束發放"
```

兌換端 `PresentVoucherApiController.AddToCart` 完全不讀這三個欄位，它只看單張券（已使用／已過期）、缺貨、購物車限購、持券守門。

**所以現在把「開放兌換」關掉，客人手上的券照樣換得到**，客服會以為關掉就停了，這是會做錯決定的等級，不只是命名不順。

### 要改哪幾處

| # | 位置 | 怎麼改 |
| --- | --- | --- |
| G-1 | `PresentVoucherService.Issue()` :164~166 | 三道 guard 拿掉。發券不再受這三個欄位限制，擋發券的只剩 `IssueCap`、`AllowRepeat` 與冪等那幾道 |
| G-2 | `PresentVoucherApiController.AddToCart` | 加上券種層檢查：不可兌換或 `now < 可兌換起日` 時擋下（後端這一道是保險，正常操作按鈕根本按不下去）|
| G-3 | `GetMemberVoucherCards` / `GetMemberVoucherCard` | 卡片 DTO 要多帶「現在能不能兌換」與起日，讓前台畫得出按鈕的停用狀態。**券本身照樣要回**，不能因為還沒到起日就從清單裡濾掉 |
| G-4 | 前台券卡片（`app-gift-list.html`、`member-center-c.html` 對應的真實頁）| 券照常顯示，兌換按鈕停用、文字「**尚未到達兌換時間**」，標籤寫出起日。**demo 已畫**（2026-09-21），見下方 |
| G-5 | `BabyBirthdayPresentBatch.cs:102` | 目前拿 `type.Display` 決定生日禮排程要不要發券。語意換掉之後這條要改判斷依據，**否則關掉「開放兌換」會連生日禮排程一起停掉**，而那不是操作的人預期的 |
| G-6 | `PresentVoucherTypeDto` 與 `PresentVoucherEntities.cs` 的 XML 註解 | `Display` 現在寫「券種啟用。關掉之後不再發新券，已發的不受影響」、`StartTime` 寫「券種啟用區間」，語意換掉後兩條都要改寫，不然下一個看註解的人會再錯一次 |
| G-7 | 欄位改名 | `Display` ⇒ `IsRedeemable`、`StartTime` ⇒ `RedeemStartTime`。`Display` 字面是「顯不顯示」，而規格是照常顯示只是不能按；`StartTime` 在這個 codebase 裡到處是「上架／贈送期間」（`ProductDetail.StartTime`），留著會被讀成發券期間。**分支還沒併 `dev`，`20260909_DEV-3963_2_presentvoucher-tables.sql` 一起改成本最低** |

## H. 建單頁的購物車：分產線、分溫層，運費各組各自算（2026-09-21 重做）

### 原本錯在哪

demo 的購物車是一張平表，運費用「整車小計 ≥ 1500 就免運，否則 150」一句話算完。**正式站不是這樣**，而且差距大到會讓客服對不上帳。

### 正式站的實際結構

| 層 | 依據 | 做什麼 |
| --- | --- | --- |
| 拆單 | `Cart.UpdateOrdersData`（`Cart.cs:2076`）`GroupBy(g => g.Type)` | 一條產線一個 `CartOrder` |
| 畫面分區 | `_CartItems.cshtml` | 一個 `CartOrder` 一個區塊，區塊底部各自有「金額／運費」。**產地直送的品項被整批抽出來放到最後一區**（原始碼註解寫「在產地直送同一個農友能合併出單前，所有產地直送要放在一起顯示」）|
| 溫層分組 | `_CartItems.cshtml` 區塊內 `GroupBy(g => g.TemperatureTypeName)` | 溫層一個小標 |
| 運費 | `LogisticsComponent.cs:120-186` ＋ `Program.cs:105-141` | **免運門檻按產線總額算，各溫層金額合併；整條產線只收一次運費** |

### 免運門檻按產線總額合併（2026-09-22 實測更正）

`Program.cs:137` 寫的是 `cartOrder.OrderFreight += item.Freight`，字面看像逐溫層各算一次再累加，**但實測不是**。粥寶寶是唯一實際會跨溫層的產線，查正式庫同次結帳拆出來的訂單對：

| 訂單 | 冷凍 | 常溫 | 合併 | 運費 |
| --- | --- | --- | --- | --- |
| `1909747` ＋ `1909748` | 840 | 837 | 1,677 | **0（免運）** |
| `1909470` ＋ `1909471` | 399 | 1,332 | 1,731 | **0（免運）** |
| `1909586` ＋ `1909587` | 939 | 954 | 1,893 | **0（免運）** |
| `1910471` ＋ `1910472` | 708 | 720 | 1,428 | 150 |
| `1910465` ＋ `1910466` | 679（有含運商品）| 300 | 979 | 100 |

**單看任一溫層都不到 1,500，合併之後超過就免運。** `1909470` 最清楚：冷凍只有 399，離 1,500 很遠，但跟常溫的 1,332 合起來 1,731 就免運了。

所以：

| 層 | 決定什麼 |
| --- | --- |
| **產線** | 免運門檻（各溫層金額合併去比）、收不收運費、收多少 |
| **溫層** | 只決定費率（粥寶寶／益菓保的常溫 100、其餘 150），以及含運商品讓所在那一組的費率變 0 |

未達門檻時收各溫層費率裡**最大**的那一筆，不是加總。`1910465` 收 100 就是這樣來的：冷凍那組有「【限時免運】小寶寶 八口味米糊」（`IsShipping = true`）所以那組是 0，只剩常溫的 100。

⚠ 建單時 `OrderModel.SplitCartOrderByTemperatureLayer`（`OrderModel.cs:9771`）會把跨溫層的購物車再拆成多張訂單，第一張 `Method.Clone` 帶走運費、其餘 `new CartOrder` 是 0。所以**正式庫查不到跨溫層的單**（抽查最近 20,000 張，零筆），要驗證得比對同一次結帳拆出來的那幾張。

⚠ 只有**粥寶寶**實際會跨溫層。益菓保只有常溫（32 個上架商品）、冷凍專區幾乎都是冷凍（393 比 1）、產地直送恆免運。快速到貨雖然常溫 3,918、冷藏 22,435 都有量，但抽樣裡跨溫層拆單的幾乎都是粥寶寶。

### GetFreight 的分支（`LogisticsComponent.cs:206-247`），由上而下

| 條件 | 運費 |
| --- | --- |
| 該組沒東西 | 0 |
| 產線是**產地直送／箱類／週期性商品** | **0（恆免運）** |
| 查不到 `ShippingRules` | 150 |
| 該組有任一**含運商品**（`IsShipping`）| **0** |
| 該組 `Σ(單價 × 數量)` < 免運門檻 | 收 `rule.Shipping` |
| 該組 `Σ(單價 × 數量)` ≥ 免運門檻 | 0 |

**門檻基數不含禮物。** 禮物是 0 元商品，不會幫忙墊到門檻，所以只兌換禮物的那一組小計是 0、照樣未達門檻、照樣收運費（`01_禮物券機制.md` 第 442 行）。這是規格，不是 bug。

改數量會**整車重算**：它會改變該組達不達免運門檻，運費跟著變。
- 右欄金額區的運費多一份明細，列出每一段是哪個產線哪個溫層、還差多少、收多少。只給一個總數客服看不懂為什麼是 400
- 產線名全部換成 `Constant.ProductCategoryEnum` 的真名。**之前 demo 用的「蔬菜箱」「水果」「鮮乳」「綠時光專區」在 enum 裡不存在**，優惠券的產線限制也跟著換（`COUPONS[].lines`）
- 每一筆商品多了 `temp`（溫層）與 `ship`（出貨時間）兩個欄位，`PRODUCTS` / `PRODUCTS_SRC` / `SRC_ORDER` / `PRESENT` 四份假資料都補齊
- 禮物的產線／溫層跟著**實際會送出的那一份**走，不是券原本綁的那一份：備援品可能在別的溫層，取錯會算錯運費（`resolve()`）

### 預設購物車演的是什麼

| 產線 | 溫層組 | 產線金額 | 免運狀態 | 產線運費 |
| --- | --- | --- | --- | --- |
| 快速到貨 | 常溫（高麗菜 ×2）120、冷藏（鮮乳 ×2）300 | 420 | 還差 1,080 | **150** |
| 產地直送 | 常溫（水果禮盒）520 | 520 | 不收運費 | 0 |

小計 940、運費 150。**再加一張生日禮券**，多一條粥寶寶專區：金額 0、還差 1,500、運費 100。那 100 就是「禮物 0 元不墊門檻」的畫面證據，也是客服最常被問的數字。

快速到貨那條刻意跨兩個溫層，用來演**門檻是合併算的**：120 ＋ 300 ＝ 420，差額寫 1,080（不是常溫差 1,380、冷藏差 1,200 兩個數字）。把鮮乳拉到 10 瓶，產線金額 1,620 ⇒ 整條免運，即使常溫那組只有 120。
